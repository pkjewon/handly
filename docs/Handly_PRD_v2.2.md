## 2. 배경과 문제

### 2-1. 아이디어 출발점 **[확정]**
고모부가 대면 초급반 수업과 농인 모임을 통해 수어를 배운 경험에서 출발했습니다. 고모부가 말한 문제는 네 가지입니다.

| # | 문제 | 이 문서에서 연결되는 기능 |
|---|---|---|
| P1 | 커리큘럼대로만 가는 일방향 수업이라 중도 포기가 많음 | M2 따라 하기(즉시 피드백), M4 짧은 단계 |
| P2 | 외국어를 원어민과 연습하듯, 실제 수어 사용자와 대화하고 싶음 | M5 연습 대화, M6 실제 대화 |
| P3 | 내가 수어를 하는 연습에 비해 **남의 수어를 읽는 연습**이 부족함 | M3 읽기 연습 |
| P4 | 학습 단계를 짧고 잘게 나눠야 동기가 유지됨 | M4 짧은 단계 학습 경로 |

> P3, P4는 문제의식만 확정이고, 이를 해결하는 기능(M3, M4)은 이 문서에서 처음 구체화한 **[제안]**입니다.

### 2-2. 근거 통계 **[확정: 30.1%로 통일]**
- 국립국어원 「2023년 한국수어 활용 조사」 기준 **30.1%** (주 의사소통 수단으로 수어를 쓰는 비율로 사용)
- 모든 문서(PPT·사업계획서·발표 대본)에서 이 수치 하나만 씀. 사업계획서에 있던 3.4%는 30.1%로 고쳐야 함

## 3. 목표와 범위

### 3-1. 목표
1. 혼자서도 카메라 피드백으로 수어 단어를 배울 수 있게 한다. **[확정]**
2. 배운 수어를 실제 농인과의 대화로 연결한다. **[확정]**
3. 하기(표현)뿐 아니라 읽기(이해) 연습까지 제공한다. **[제안]**
4. 짧은 단계와 게임 요소로 중도 포기를 줄인다. (게임 요소 **[확정]**, 방식 **[제안]**)

### 3-2. 이번 범위에서 하지 않는 것
- 문장 단위 실시간 수어 번역 (현재 인식 수준과 차이가 큼) **[제안]**
- 대화 중 AI가 학습자 수어를 실시간으로 알아듣는 기능 — 대화 기능에서 AI는 힌트와 연습 채점까지만 **[제안]**
- 표정·입모양(비수지 신호) 인식 — 이번에는 손 동작만 보고, 나중에 추가 (17장) **[확정]**
- 유료 서버·유료 서비스 사용 — 무료로 쓸 수 있는 것만 사용 (10-6) **[확정]**

## 5. 기존 서비스와 차별점

이미 비슷한 서비스가 있어서 "최초"가 아니라 "차별점"으로 설명해야 합니다.

| 서비스 | 내용 (조사 당시 기준) |
|---|---|
| 수어통에듀 (이큐포올) | 국내 카메라 기반 수어 학습 |
| NVIDIA Signs | 해외(미국수어) 카메라 피드백 학습 플랫폼 |
| PopSign | 해외 수어 학습 게임 |

**Handly 차별점 후보 [제안]**
1. **학습 → 실제 농인 대화까지 한 흐름**으로 연결 (P2)
2. **읽기 연습** 포함 (P3)
3. 짧은 단계 + 게임 요소 (P1, P4)
4. 농인을 유료 튜터로 두어 **농인 일자리** 창출 (사업 모델)

> 기존 서비스가 위 기능을 이미 갖고 있는지는 아직 자세히 비교하지 않았습니다. **[확인 필요]**

## 7. 전체 학습 흐름

```
[M4 학습 경로: 짧은 단계로 나뉜 레슨]
        │
        ▼
① 배우기 (M1)  ──  입체 손 안내 + 여러 사람·각도 영상
        ▼
② 따라 하기 (M2)  ──  카메라 인식, 초록/빨강 피드백
        ▼
③ 읽기 연습 (M3)  ──  남의 수어 영상 보고 뜻 맞히기
        ▼
④ 연습 대화 (M5)  ──  녹화된 대화 영상 + AI 채점
        ▼
⑤ 실제 대화 (M6)  ──  농인 튜터와 영상 대화
```

①②는 확정된 흐름, ③은 추가한 **[제안]**, ④⑤의 순서(연습 후 실제 대화로 연결)는 **[제안]**입니다.

## 8. 기능 요구사항

우선순위: **필수** / 권장 / 선택

### M1. 단어 배우기

| ID | 기능 | 설명 | 우선순위 | 상태 |
|---|---|---|---|---|
| M1-1 | 단어 카드 | 단어 이름, 뜻, 동작 설명(손 모양·위치·움직임) | 필수 | [확정] |
| M1-2 | 입체 손 안내(A안) | 기준 좌표(M7-1)로 그린 두 손 + 흐린 머리·어깨 선, 반복 재생. "동작 구조 보기" 역할 | 필수 | [확정] |
| M1-3 | 실제 손 영상(B안) | 영상에서 손 영역만 남긴 실제 손. A안이 어색할 때만 | 선택 | [확정] |
| M1-4 | 여러 영상 보기 | 단어별로 여러 사람·여러 각도 영상. "실제 모습 보기" 역할 | 필수 | 기능 [확정] / 세부 [제안] |
| M1-5 | 영상 종류 탭 | 기본(정면) / 천천히(0.5배속) / 다른 각도(옆) / 여러 사람 / 문장 속에서 / 다른 표현(지역·세대 차이) | 권장 | [제안] |
| M1-6 | 반복·속도 조절 | 구간 반복, 0.5·0.75·1배속 | 권장 | [제안] |

### M2. 따라 하기 (카메라 인식)

| ID | 기능 | 설명 | 우선순위 | 상태 |
|---|---|---|---|---|
| M2-1 | 두 손 인식 | 두 손 동시 추적(num_hands=2). 손이 안 잡힌 프레임 처리는 10-3 규칙을 따름 | 필수 | [확정] |
| M2-2 | 위치 보정 | 어깨 기준으로 손 좌표 정규화 (거리·체격 차이 보정). 방법은 10-3 | 필수 | [확정] |
| M2-3 | 실시간 손 표시 | 웹캠 위에 손 관절 점·선 표시 | 권장 | [제안] |
| M2-4 | 카운트다운 녹화 | 3·2·1 후 약 3~4초 동안 학습자 좌표 기록 | 필수 | 카운트다운 [확정] / 시간 [추정] |
| M2-5 | 동작 판정 (DTW) | 녹화한 좌표 시퀀스를 단어별 기준 동작과 **DTW 거리**로 비교. ① 목표 단어 기준까지의 거리가 그 단어의 기준값 이하이고 ② 목표 단어가 모든 단어 중 가장 가까우면 **정답**, 아니면 **오답** | 필수 | DTW [확정] / 판정 규칙 [제안] |
| M2-5a | 오답 동작 처리 | 가만히 있기·아무렇게나 손 흔들기·다른 단어 섞기 등 오답 동작을 녹화해 둠. 기준값을 정할 때 오답 동작의 거리가 모두 기준값보다 멀게 나오는지 확인 → 엉뚱한 동작이 정답 처리되지 않게 함 | 필수 | [제안] |
| M2-6 | 결과 표시 | 대기 회색 / 정답 초록 / 오답·인식 실패 빨강 + 안내 문구 | 필수 | 초록·빨강 [확정] / 회색 대기 [제안] |
| M2-7 | 틀린 이유 힌트 | 점수가 낮을 때 원인 안내. DTW가 짝지어 준 프레임끼리 학습자 좌표와 기준 좌표를 직접 비교해 계산 (아래 표) | 권장 | 기능 [제안] / 방법 [제안] |
| M2-8 | 기준값 조정 도구 | 제작자가 단어별 정답 기준(DTW 거리 기준값)을 조정하는 도구. 정답 테이크·오답 테이크의 거리 분포를 보고 그 사이로 정함 | 권장 | [확정] |

**M2-7 힌트 계산 방법 [제안]**

| 힌트 | 계산 |
|---|---|
| "손 위치가 낮아요/높아요" | 짝지어진 프레임들의 손목 높이(y) 평균 차이가 일정 값 이상 |
| "손을 더 몸 쪽으로/바깥쪽으로" | 손목 x 평균 차이 |
| "동작이 너무 빨라요/느려요" | 학습자 동작 시간 ÷ 기준 동작 시간 (예: 0.6배 미만이면 빠름, 1.6배 초과면 느림) |
| "두 손이 화면에 나오게 해 주세요" | 10-3의 손 없음 규칙에 걸린 경우 |

> 앱 단계에서 LSTM/GRU 모델로 판정을 바꾸더라도, 모델은 "어느 단어일 확률"만 알려주기 때문에 힌트는 이 기준 좌표 비교 방식을 그대로 씁니다.

### 10-3. 좌표 처리 규칙 (시연·앱 공통) [제안]

```
① 촬영 → ② 좌표 추출 → ③ 정리(왼/오손 구분·빈 프레임 처리·정규화·시간 맞춤) → ④ DTW 비교 → ⑤ 판정·힌트
```

기준 동작(M7-1)과 학습자 동작은 **반드시 같은 규칙으로** 처리합니다. 처리 방식이 다르면 같은 동작도 다르게 나옵니다.

**프레임 하나의 데이터**
- 왼손 21점, 오른손 21점 (각 x, y, z)
- 어깨 기준점 (왼쪽·오른쪽 어깨)
- "왼손 있음", "오른손 있음" 표시값 (0 또는 1)

**왼손/오른손 구분**
- MediaPipe가 주는 왼손/오른손 라벨은 가끔 뒤바뀌므로 그대로 믿지 않음 (앱의 `hand_landmarker` 패키지는 문서상 왼/오 라벨 제공이 확인되지 않음 → 이 규칙이 있으면 라벨이 없어도 됨)
- 손목이 몸 중심(두 어깨의 가운데)보다 화면 어느 쪽에 있는지로 다시 정함
- 웹캠 좌우 반전 여부는 기준 녹화와 학습자 화면에서 똑같이 맞춤

**손이 안 잡힌 프레임**

| 상황 | 처리 |
|---|---|
| 짧게 끊김 (약 0.2초 이하) | 앞뒤 프레임 좌표로 채움 (선형 보간) |
| 길게 끊김 | 그 손을 "없음"으로 표시 |
| 한 손 단어 | 기준 동작에서 안 쓰는 손은 비교에서 뺌 |
| 두 손 단어인데 한 손이 오래 없음 | 판정하지 않고 빨강 + "두 손이 화면에 나오게 해 주세요" |
| 녹화 구간 절반 이상에서 손이 없음 | 인식 실패 (빨강 + 안내 문구) |

**정규화**: 두 어깨의 가운데를 원점(0, 0), 어깨 너비를 1로 맞춤 → 카메라 거리·체격 차이 보정

**시간 기준 길이 맞춤**
- 촬영은 60fps, 노트북 웹캠은 보통 30fps라서 프레임 개수로 맞추면 속도가 틀어짐
- 모든 데이터를 **1초당 30개**로 다시 샘플링 (각 프레임의 실제 시간 위치를 기준으로 보간)
- DTW는 길이가 달라도 비교할 수 있으므로 시연에서는 이것만 하면 됨. 모델(10-4)은 추가로 고정 길이로 맞춤

**판정**: M2-5 규칙 (거리 기준값 이하 + 목표 단어가 가장 가까움)

### 10-4. AI 모델 (앱 단계, 시연과 병행 개발) [제안]

```
① 촬영 (웹캠·휴대폰)
      ▼
② 좌표 추출 + 10-3 정리 규칙 그대로 적용
      ▼
③ 고정 길이로 맞춤 (예: 30프레임)
      ▼
④ 데이터 저장 (npy/CSV → Google Drive)
      ▼
⑤ 학습 (Google Colab + PyTorch)
   - LSTM과 GRU를 둘 다 학습해 정확도·속도 비교 후 선택
   - 출력: 단어 N개 + "오답" 클래스
   - 판정: 목표 단어가 1등이고 확률이 단어별 기준 이상이면 정답
      ▼
⑥ 앱에 넣기: 모바일용 형식으로 변환 후 Flutter에 포함 → 기기 안에서 판정
```

**데이터 증강 (촬영 부담 줄이기)**

| 방법 | 사용 | 이유 |
|---|---|---|
| 작은 회전 (±10도 정도) | 사용 | 몸을 살짝 기울인 경우 대비 |
| 크기 변화 (±10% 정도) | 사용 | 손 크기·팔 길이 차이 대비 |
| 속도 변화 (0.8~1.2배) | 사용 | 사람마다 동작 속도가 다름 |
| 약한 노이즈 (좌표를 아주 조금 흔듦) | 사용 | MediaPipe 좌표 떨림 대비 |
| 위치 이동 (좌우·상하) | 사용 안 함 | 어깨 기준 정규화를 하면 이동이 없어져서 효과 없음 |
| 좌우 반전 | 감수 전에는 사용 안 함 | 왼손잡이 대비는 되지만 뜻이 바뀌는 단어가 있을 수 있음 |

- 앱에서 PyTorch 모델을 돌리는 방법(TFLite 변환, ONNX 변환 등)과 Flutter용 패키지는 **[확인 필요]**. 작은 모델로 변환 테스트부터 해보기.
- 변환이 안 되면 앱 MVP는 DTW를 그대로 사용 (13장)
- 판정은 **기기 안에서만** 함 (10-6 비용 원칙). 좌표를 서버로 보내서 판정하는 방식은 서버 비용이 들어서 쓰지 않음. 기기 안 판정은 카메라 영상을 밖으로 보내지 않아서 M8-1과도 맞음.

### 10-8. 앱의 어깨 기준점 구하기 **[확정: 어깨 기준 정규화 유지]**

**결정**: 손만으로 정규화하는 방식은 쓰지 않고, 어깨 기준을 유지함.
- 이유 1: 수어는 손이 몸의 어디에 있는지(얼굴 앞·가슴 앞 등)도 뜻의 일부라서, 손만 보면 위치만 다른 단어를 구별 못 함
- 이유 2: M2-7 "손 위치가 낮아요" 힌트는 몸 기준이 있어야 계산 가능
- 이유 3: 시연 프로그램·기준 좌표가 이미 어깨 기준이라 다시 만들 필요 없음

**앱 구성 (2026-10 패키지 확인 결과)**

| 역할 | 패키지 | 확인한 내용 |
|---|---|---|
| 손 21점 × 2 | `hand_landmarker` 3.1.0 | MediaPipe Hand Landmarker 기반, 안드로이드 전용, numHands=2 가능, 좌표는 0~1 정규화 값, Flutter `camera`의 `CameraImage`를 그대로 입력. 왼/오 라벨 제공은 문서에 없음 |
| 어깨 기준점 | `google_mlkit_pose_detection` 0.16.1 | Google ML Kit 포즈 인식(BlazePose 계열), 33점(어깨·코·입·귀 포함), 안드로이드·iOS 지원, 2026년 8월 업데이트, 인증된 배포자(flutter-ml.dev). 좌표는 이미지 픽셀 단위 |

**맞춰야 할 것**
- 같은 카메라 프레임(`CameraImage`)을 두 패키지에 같이 넣음
- ML Kit 어깨 좌표(픽셀)를 이미지 너비·높이로 나눠서 손 좌표(0~1)와 단위를 맞춤
- 화면 회전·좌우 반전을 두 패키지에서 똑같이 맞춤
- 속도가 부족하면 어깨는 2~3프레임에 한 번만 계산 (어깨는 수어 중 거의 안 움직임) **[추정]**

**Python(시연)과 앱의 차이**: Python은 MediaPipe Pose Landmarker, 앱은 ML Kit을 씀. 둘 다 BlazePose 계열 33점 구조라 어깨 위치가 비슷할 것으로 보지만 완전히 같은 모델이라는 확인은 못 함 **[추정]**. 어깨 가운데·어깨 너비만 쓰기 때문에 작은 차이는 영향이 적을 것으로 봄 **[추정]**

**앱 개발 전 테스트 (작은 테스트 앱)**

| # | 확인할 것 | 통과 기준 [제안] |
|---|---|---|
| 1 | 두 패키지를 한 화면에서 같이 돌릴 수 있는지 | 손 점·어깨 점이 동시에 화면에 표시됨 |
| 2 | 속도 | 두 개 같이 돌려서 초당 15프레임 이상 |

**테스트 환경 [확정]**: 개발은 노트북에서, 속도 확인은 실제 폰에서

| 환경 | 방법 | 할 수 있는 것 |
|---|---|---|
| 노트북 (안드로이드 에뮬레이터) | Android Studio에서 가상 기기(AVD) 만들고 Front Camera를 `Webcam0`으로 설정 → 노트북 웹캠을 폰 카메라처럼 사용 | 위 테스트 1·3, 앱 화면·레슨 흐름, Firebase 연결 등 대부분의 개발 |

- 에뮬레이터 속도는 노트북 성능을 따라가서 실제 폰과 다름 → 속도 판단은 실제 폰으로만 **[추정]**
- MediaPipe(`hand_landmarker`)가 에뮬레이터에서 잘 돌아가는지는 아직 확인 못 함. GPU 가속이 안 될 수 있어 CPU 모드로 실행해야 할 수 있음 **[확인 필요]**
- 참고: 앱 개발이 계속 막히면 MediaPipe 웹(JavaScript) 버전으로 노트북 브라우저에서 돌리는 방법도 있음 (스택 변경이라 지금은 안 씀)

**안 될 때 대안 (순서대로)**
1. `hand_landmarker`는 Kotlin(JNI)으로 MediaPipe를 부르는 구조라, 이 코드를 가져와 MediaPipe Pose Landmarker를 같이 부르도록 수정 (Python과 같은 모델이 됨, 대신 Kotlin 작업 필요)
2. 그래도 안 되면 손만으로 정규화 (기준 좌표 다시 만들고, M2-7 위치 힌트는 뺌)

> 참고: MediaPipe 전체를 Flutter로 옮긴 프로젝트(`mediapipe_flutter`)도 있지만, 안드로이드 실기기에서는 아직 검증 안 됐다고 적혀 있어서 쓰지 않음.
